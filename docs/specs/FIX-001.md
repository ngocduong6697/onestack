# FIX-001 — Intermittent foreign 404s in the end-to-end suite

Not a backlog task. Recorded because the diagnosis took long enough to be
worth writing down, and because the failure mode is one any future test file
could reintroduce.

## Symptom

Roughly one full backend suite run in three failed. The failures were bursts
in whichever file happened to be running, either 404s on routes that plainly
exist — `POST /auth/register`, `GET /auth/me` — or timeouts once a test's
setup had already failed. The suite was clean at TASK-006 (16 consecutive
runs) and became unreliable when TASK-007 added a sixth end-to-end file, so
volume was the trigger rather than any particular test.

## Cause

`supertest` starts a server for the request when the one it is handed has no
address, and closes it again when the request finishes. Each file was calling
`app.init()` — which does not listen — so every one of roughly two hundred
requests per file opened an ephemeral port and released it.

Occasionally a request went out to a port that had just been released and
reassigned to another listener on the machine, and that listener answered.
The reply was a bare 404: empty body, `connection: close`, and none of the
shape this application produces — the exception filter always writes an
`error` object, and Nest's own router 404 carries a JSON body.

The diagnostic that settled it recorded the response alongside
`app.getHttpServer().address()`:

```
GET /orgs failed
  status:  404
  server:  null
  headers: {"date":"...","connection":"close","transfer-encoding":"chunked"}
  text:    ""
```

`server: null` shows our server was not listening at that moment, and the
request never appeared in the application's own request log — 206 requests
logged, every one of them answered normally. It had gone somewhere else.

## Fix

`await app.listen(0)` instead of `await app.init()` in every end-to-end file.
One port is held for the lifetime of the file, so supertest reuses it and
never opens or closes another. The churn disappears, and the race with it.

## Evidence

|                       | Before              | After           |
| --------------------- | ------------------- | --------------- |
| Full suite            | ~1 run in 3 failed  | 25 of 25 passed |
| `customers.e2e` alone | ~1 run in 20 failed | 25 of 25 passed |

## What was ruled out first, and how

Each of these was measured, not reasoned about, and each was wrong:

- **A shared database.** Giving every file its own database made it _worse_
  and was reverted.
- **Connection pool exhaustion.** A pool of one is clean, which a leak would
  deadlock immediately.
- **Password hashing cost.** 10 ms a hash, 179 ms for twenty in series.
- **Socket exhaustion.** 470 sockets in `TIME_WAIT` against 16,384 ephemeral
  ports — the right neighbourhood, wrong mechanism.
- **libuv thread starvation.** 32 threads changed nothing.
- **Process accumulation.** One process per file still flaked.
- **HTTP keep-alive.** Disabling it changed nothing.
- **File parallelism.** Lifecycle timestamps proved the files were already
  strictly sequential; pinning a single fork changed nothing.

The lesson worth keeping: the first useful evidence arrived only when the
failing response was captured whole — status, headers, body and server
address — rather than asserted against. Six hypotheses died in the time it
took to print one response.

## Also kept

The setup helpers in the end-to-end files now assert their own responses, so
a failure during `signUp` names itself instead of surfacing later as
`undefined.id` and pointing at an unrelated test.
